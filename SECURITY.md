# Security Model — Loan Management Workshop Sample

This document explains the security stance of the sample, the **demo-only** trade-offs
we made, and the concrete path to harden it for production.

## Threat model (workshop scope)

The sample is designed to run in:
- **Workshop Studio**: a per-participant AWS account, fronted by CloudFront/ALB.
- **Local Docker Compose**: a single developer's laptop, behind localhost only.

The threat model assumes:
- No untrusted multi-tenancy. The whole stack is dedicated to one participant.
- No real PII. The "customers" are demo personas seeded with synthetic data.
- No regulated workloads. Loan/credit decisioning logic is illustrative only.

This means the sample focuses on **showing the right shape** for auth,
authorization, secrets handling, and infrastructure isolation — not on shipping
a hardened bank.

## Secrets handling

| Secret                  | Workshop Studio (CDK)                                                | Local Docker dev                          |
|-------------------------|----------------------------------------------------------------------|-------------------------------------------|
| RDS master password     | `secretsmanager.fromGeneratedSecret` → injected into ECS via secrets | `.env` (gitignored), strong random        |
| JWT signing key         | `secretsmanager` 64-char random → ECS secret                         | `.env`, generated by `scripts/generate-env.sh` |
| Redis AUTH token        | `secretsmanager` 32-char random → ECS secret + transit encryption    | `.env`, optional                          |
| Demo admin password     | Fixed, well-known value seeded on first boot (workshop only) — see README "Sign in" section | Same value; `generate-env.sh` only generates secrets that are not the demo admin password |
| AWS account ID          | `process.env.CDK_DEFAULT_ACCOUNT` (Workshop Studio injects)          | `aws sts get-caller-identity`             |
| DevOps Agent webhook    | AWS Secrets Manager (`loan-management/devops-agent-webhook-secret`) created only when `-c devops_agent_webhook_secret` is set | `.env`                                    |

Nothing in the repository contains real secret material. Every secret is
either (a) generated at deploy / first-boot time, or (b) sourced from env
or a secret store. The `.gitignore` blocks `.env`, `cdk.out`, and build
artefacts from being committed.

## Authentication & authorization

- **JWT validation** (`shared/middleware/__init__.py`):
  - `JWT_SECRET` is **required** — there is no fallback. Services refuse to start without it.
  - Tokens carry `iss` (`loan-management-system`), `aud` (`loan-management-api`),
    `iat`, `exp`, and a unique `jti`. We validate all of them.
  - Refresh tokens are rotated on use (`is_revoked = True`) and stored in the DB.
- **Login rate limiting** (`auth-service`): default `10/minute` per IP via `slowapi`.
- **Password policy**: 12–128 chars, must include lower, upper, digit, and symbol.
- **Authorization** uses a small RBAC: `ADMIN`, `LOAN_OFFICER`, `UNDERWRITER`,
  `COLLECTIONS_AGENT`, `CUSTOMER`. Sensitive endpoints are gated by `require_role(...)`.
  Per-customer endpoints additionally enforce ownership (`customer.user_id == current_user.sub`).

### Why no `localStorage` for tokens?
The frontend keeps the access token in `sessionStorage` plus an in-memory
fallback. A future iteration could move to httpOnly refresh-token cookies —
that's left as an exercise to keep the sample a single-page app.

## Network and infrastructure

- VPC isolation: RDS + Redis live in `PRIVATE_WITH_EGRESS` subnets, no public IPs.
- Security groups: ALB ↔ ECS, ECS ↔ RDS, ECS ↔ Redis only.
- ALB:
  - Optional HTTPS listener via `-c certificateArn=...`.
  - Access logs to S3 (30-day lifecycle).
  - WAFv2 attached: `AWSManagedRulesCommonRuleSet`, `KnownBadInputsRuleSet`,
    plus a per-IP rate-based rule (2000 / 5min).
  - `dropInvalidHeaderFields: true`.
- CloudFront:
  - `BlockPublicAccess.BLOCK_ALL` on the S3 origin.
  - Origin Access Control (OAC) for S3.
  - `REDIRECT_TO_HTTPS` for viewers.
- Redis: `transitEncryptionEnabled`, `atRestEncryptionEnabled`, AUTH token.
- RDS: `storageEncrypted: true`, IAM authentication, PostgreSQL log export.
  Multi-AZ + 7-day backups + deletion protection in `productionMode`.
- ECR: AES-256 encryption, scan on push, immutable tags in `productionMode`.

## Application-layer

- All FastAPI services use a **shared CORS helper** that reads
  `CORS_ALLOWED_ORIGINS` from env. There are no `*` defaults outside of the
  `local` environment, and `local` defaults to `http://localhost:*` only.
- Nginx no longer emits permissive CORS — it adds the standard set of
  security headers (`X-Content-Type-Options`, `X-Frame-Options: DENY`,
  `Referrer-Policy`, `Permissions-Policy`, HSTS).
- All SQL goes through SQLAlchemy ORM or parameterized `text(... :bind ...)` —
  no f-string SQL anywhere.

## Demo-only trade-offs (why this isn't yet production-grade)

These choices are intentional for a self-contained workshop, and each comes
with a clear "harden for production" path:

| Demo choice                                   | Production hardening                                       |
|-----------------------------------------------|------------------------------------------------------------|
| Single Redis node, no replicas                | Add replicas + multi-AZ in `productionMode`                |
| Same JWT secret across services               | Issue per-service public-key (RS256) tokens                |
| Access tokens cannot be revoked early          | Add a JTI denylist in Redis, check on every request        |
| KYC auto-verifies after 3s in `customer-service` | Wire to a real KYC provider; gate behind admin override |
| `EMAIL_SIMULATION=true`                       | Replace `notification-service` adapter with SES            |
| Frontend keeps token in `sessionStorage`      | httpOnly refresh-token cookies + short-lived access tokens |
| Demo seed creates 5 personas                  | Disable seed (`ENABLE_DEMO_SEED=false`) and self-register  |
| Image tag `latest` (workshop ergonomics)      | Use commit SHA tags + `imageTagMutability: IMMUTABLE`      |
| Stress-test endpoint exists                   | Remove `loan-service` chaos path, run chaos via Fault Injection Service instead |

## Reporting issues

This is a sample repository. If you find a vulnerability that affects the
patterns demonstrated here (rather than your own deployment of them), please
open a private security advisory rather than a public issue.
